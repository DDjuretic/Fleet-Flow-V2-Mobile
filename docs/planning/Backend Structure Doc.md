# Backend Structure Document

## 1. Overview
- The backend is provided by Supabase, a Backend-as-a-Service (BaaS) platform.
- This abstracts away much of the traditional server-side infrastructure management.
- Supabase uses PostgreSQL as its underlying database.

## 2. Technology Stack
- Platform: Supabase
- Database: PostgreSQL
- APIs: Auto-generated RESTful APIs (PostgREST), Realtime subscriptions, GraphQL (optional)
- Authentication: Supabase Auth (JWT-based, social providers, etc.)
- Serverless Functions: Supabase Edge Functions (Deno, TypeScript/JavaScript) if custom server-side logic is needed beyond basic CRUD.
  - **Note:** For critical, transactional business logic, **PostgreSQL RPC (Remote Procedure Call) functions are preferred** due to their atomicity, simplified debugging, and closer integration with the database. Edge Functions are better suited for asynchronous tasks, webhooks, or external integrations.

## 3. Folder Structure
- While Supabase manages the core backend infrastructure, code related to the backend (like database migrations and serverless functions) resides within the project repository.
- The primary backend-related folder is `supabase/`:
  - `supabase/migrations/`: Contains all SQL migration files for schema changes and data seeding.
  - `supabase/functions/`: Contains Supabase Edge Functions written in TypeScript/JavaScript (Deno runtime).
  - `supabase/seed.sql`: Initial data seeding for new environments.

## 4. API Design
- Primarily RESTful APIs automatically generated by Supabase based on the PostgreSQL schema.
- Realtime capabilities for live data synchronization.
- Supabase client library (`@supabase/supabase-js`) is used on the frontend to interact with these APIs.
- Authentication is handled via JWTs managed by Supabase Auth. For more details, see [Auth Management Guide](../AUTH_MANAGEMENT_GUIDE.md).
- Authorization is managed through PostgreSQL Row Level Security (RLS) policies and database roles.
- **Complex Business Logic (e.g., Travel Order Cost Calculation):** Implemented primarily as **PostgreSQL RPC functions** (stored procedures) to ensure data integrity and efficient execution directly within the database. These functions are then exposed via Supabase API and called from the frontend.

## 5. Database Schema
- The database schema is defined and managed through SQL migration files located in `supabase/migrations/`.
- All schema changes, including table definitions, RLS policies, functions, and triggers, are version-controlled within these migration files.
- For a detailed overview of the core schema and planned extensions (e.g., for Travel Order, Fuel Management), refer to `docs/planning/PUTNI_NALOG_IMPLEMENTATION_PLAN.md` and the individual migration files.

## 6. Error Handling
- Supabase client library provides error objects for API request failures.
- Consistent error handling should be implemented in the frontend service layer.
- Supabase Edge Functions have their own error handling and logging mechanisms.

## 7. Testing Strategy
- For Supabase Edge Functions: Local testing using Supabase CLI, integration tests.
- Database RLS policies can be tested using SQL query tools or dedicated test scripts.
- (Frontend tests will cover API integration points)

## 8. Deployment
- Backend is managed and deployed by Supabase.
- Database migrations can be managed via Supabase CLI or UI.
- Supabase Edge Functions are deployed via Supabase CLI.

## 9. Security Considerations
- Row Level Security (RLS) is crucial and must be enabled and correctly configured for all tables.
- Secure management of API keys (anon key, service_role key).
- Input validation on the frontend before sending data to Supabase.
- If using Edge Functions, ensure they are secure and follow best practices.
- Configure network restrictions and other security features in Supabase dashboard (e.g., custom SMTP for auth emails).
